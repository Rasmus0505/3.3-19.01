## 二、架构层面关键问题（影响扩展能力）

### 2.1 巨型模块重构

#### UploadPanel.jsx — 5,792 行
- **路径**: `frontend/src/features/upload/UploadPanel.jsx`
- **问题**: 处理 15+ 种上传模式（桌面、本地浏览器、云端、链接导入、ASR-only、诊断等），包含内联 JSX 模板
- **风险**: 自身大小 = 整个 upload feature 子目录的一半（20 个文件 / 5,550 行）
- **建议**: 拆分为 UploadPanelShell（编排）+ 独立的上传模式组件，每个组件 < 500 行

#### lesson_service.py — 3,060 行
- **路径**: `app/services/lesson_service.py`
- **问题**: 导入 10+ 个其他服务，与 billing、ASR、task manager 紧密耦合
- **建议**: 按职责拆分为 lesson_read_service.py、lesson_write_service.py、lesson_orchestrator.py

#### ImmersiveLessonPage.jsx — 2,464 行
- **路径**: `frontend/src/features/immersive/ImmersiveLessonPage.jsx`
- **问题**: 42 个 `useEffect`，混合 reducer 状态和大量副作用
- **建议**: 提取自定义 hooks 分离关注点，每个 hook 专注一种副作用

#### test_regression_api.py — 7,312 行
- **路径**: `tests/integration/test_regression_api.py`
- **问题**: 118 个测试函数的巨型文件
- **建议**: 按功能域拆分为独立文件

### 2.2 API 版本化

**现状**: 所有路由硬编码 `/api/xxx` 前缀，无版本概念。部分 router（`llm_writing.py`、`llm_usage.py`）甚至没有 `/api/` 前缀。

**建议方案**:
```
Phase 1: 统一所有路由使用 `/api/` 前缀
Phase 2: 引入 `/api/v1/` 命名空间，旧路由维持向后兼容
Phase 3: 支持 `Accept-Version` header 或 URL 参数进行版本协商
```

**关键文件**: `app/main.py`（路由注册点）、`app/core/config.py`（API_VERSION 配置）

### 2.3 后台任务架构

**现状**: 使用 Python `threading` 模块在进程内运行任务，无持久化队列。

**问题**:
- 进程重启丢失所有运行中任务状态
- 多副本部署时无法水平扩展
- SQLAlchemy session 在后台线程中非线程安全
- `LESSON_TASK_MAX_ACTIVE`/`LESSON_TASK_MAX_QUEUED` 仅在内存中生效

**建议方案**:
```
短期: 将关键状态持久化到 DB，添加进程启动时的任务恢复逻辑
长期: 引入 Celery + Redis 作为分布式任务队列
```

**关键文件**:
- `app/services/lessons/task_runtime.py`（线程级信号）
- `app/services/lessons/task_workspace.py`（文件级状态）
- `app/services/lesson_task_manager.py`（任务编排）

### 2.4 错误处理统一

**现状**: 存在三种平行的错误处理模式：
- `error_response()` → JSONResponse（多数路由）
- `raise HTTPException()`（少数路由）
- 同一文件混用（`tts.py`、`soe.py`、`voice_cloning.py`）

**异常继承体系已定义但未使用**:
```
AppError → AuthError(401) / NotFoundError(404) / ValidationError(422) / 
           LessonError(400) / BillingError(402) / AdminError(403)
```

**建议**:
```python
# app/main.py 添加全局异常处理器
@app.exception_handler(AppError)
async def app_error_handler(request, exc: AppError):
    return JSONResponse(
        status_code=exc.status_code,
        content=ErrorResponse(ok=False, error_code=exc.code, message=exc.message, detail=exc.detail).model_dump(),
    )
```
然后逐步将所有路由的 `error_response()` / `HTTPException` 替换为 `raise AppError(...)`。

**关键文件**: `app/exceptions/base.py`、`app/main.py`、`app/core/errors.py`

### 2.5 数据库迁移策略

**现状**:
- 2 个正式 Alembic 迁移文件（`alembic/versions/`）
- 大部分 schema 变更通过运行时 `ALTER TABLE`（`schema_guards.py`）
- 无 `downgrade()` 路径
- 双迁移目录（`alembic/` + `migrations/`）容易混淆

**建议**:
1. 统一迁移目录，废弃其中一个
2. 所有 schema 变更通过 Alembic migration 完成
3. 每次 migration 提供 `downgrade()` 函数
4. 迁移测试在 CI 中使用 PostgreSQL 运行

**关键文件**: `app/db/schema_guards.py`、`alembic.ini`、`migrations/`

### 2.6 外部 AI 提供者抽象

**现状**: ABC 模式迁移未完成：
- ✅ `app/infra/asr/base.py` → `ASRProvider` + `DashScopeASR`
- ✅ `app/infra/tts/base.py` → `TTSProvider` + `DashScopeTTS`
- ❌ `app/infra/asr_stepfun.py` — 独立模块，未使用 ABC
- ❌ `app/infra/tencent_soe.py` — 独立模块，未使用 ABC
- ❌ 添加新 provider 需改 3+ 处代码（infra + registry + gateway）

**建议**: 完成所有 provider 的 ABC 迁移，Gateway 层使用策略模式实现动态路由。

## 四、基础设施层面

### 4.1 结构化日志

**现状**: `app/core/logging.py` 仅 9 行，无 JSON 格式、无 correlation ID、无请求追踪。

**建议**:
```python
# 使用 structlog 或 python-json-logger
import structlog
structlog.configure(
    processors=[
        structlog.stdlib.filter_by_level,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.JSONRenderer(),
    ],
)
```
